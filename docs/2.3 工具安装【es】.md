> **创建索引库 \(对应 ****`image_f74767.png`****\)**
> 
> 这段代码的目的是在数据库中建立一个名为 `user` 的“表”（在 ES 中称为索引/Index），并规定好里面有哪些字段、用什么分词器。
> 
> - `POST /user/_doc`：向名为 `user` 的索引发送请求。（注：标准的 ES 语法中，仅创建索引通常用 `PUT /user`，这里是将创建索引和设置结构放在了一起）。
> 
> - `"settings" : {`：**设置区块**。用于配置这个索引的底层参数。
> 
>     - `"analysis" : {`：配置文本分析器。
> 
>     - `"analyzer" : {`：定义自定义的分词器。
> 
>     - `"ik" : {`：给我们的自定义分词器起个名字叫 `ik`。
> 
>     - `"tokenizer" : "ik_max_word"`：核心设置。指定使用 `ik_max_word` 算法。这个算法会将中文文本做**最细粒度**的拆分（例如“中华人民共和国”会被拆成“中华”、“华人”、“人民”等），能极大提高搜索的命中率。
> 
> - `"mappings" : {`：**映射区块**。相当于关系型数据库中的“表结构设计”，用于定义各个字段（列）的属性。
> 
> 
> 
> - `"dynamic" : true`：允许动态映射。意思是如果以后插入的数据多出了没定义过的字段，ES 会自动接收并猜它的类型，不会报错。
> 
> 
> 
> - `"properties" : {`：开始具体定义每个字段的属性。
> 
> 
> 
> - `"nickname" : {`：定义“昵称”字段。
> 
> 
> 
> - `"type" : "text"`：类型为 `text`，表示这是一段长文本，**需要被分词器拆分**以便模糊搜索。
> 
> 
> 
> - `"analyzer" : "ik_max_word"`：指定搜索这个字段时，使用上面配置好的 IK 中文分词器。
> 
> 
> 
> - `"user_id" : {`：定义“用户ID”字段。
> 
> 
> 
> - `"type" : "keyword"`：类型为 `keyword`。与 `text` 不同，`keyword` **不会被分词**，必须一模一样才能匹配上（精确匹配）。
> 
> 
> 
> - `"analyzer" : "standard"`：使用标准分析器（实际上 keyword 类型通常不需要分词，这行配置属于冗余防御性写法）。
> 
> 
> 
> - `"phone" : {`：定义“手机号”字段。
> 
> 
> 
> - `"type" : "keyword", "analyzer" : "standard"`：同样是精确匹配，不能把手机号拆开来搜。
> 
> 
> 
> - `"description" : {`：定义“个人签名/描述”字段。
> 
> 
> 
> - `"type" : "text"`：文本类型。
> 
> 
> 
> - `"enabled" : false`：**关键点**。关闭这个字段的索引功能。意思是这个字段的内容会被保存在数据库里展示，但**无法用来作为搜索条件**（为了节省性能和存储空间）。
> 
> 
> 
> - `"avatar_id" : {`：定义“头像ID”字段。
> 
> 
> 
> - `"type" : "keyword", "enabled" : false`：精确匹配类型，同样不参与搜索，仅作数据存储。
> 
> 
> 
> **新增数据 \(对应 ****`image_f747a0.png`****\)**
> 
> 这段代码使用了 ES 的批量操作接口，一次性向数据库里塞入 6 条用户数据。
> 
> - `POST /user/_doc/_bulk`：调用 `_bulk`（批量）API。在这个接口下，数据必须是“两行为一组”的格式。
> 
> - `{"index":{"_id":"1"}}`：**动作行**。告诉 ES：“我要进行新增/更新（index）操作，并且强制指定这条数据的唯一 ID 为 1”。
> 
> - `{"user_id" : "USER...", "nickname" : "昵称1", ... }`：**数据行**。这才是真正要存入数据库的具体 JSON 数据内容。
> 
> - 后续的 `{"index":{"_id":"2"}}` 一直到 `6`：重复上述逻辑，连续插入了 ID 为 2 到 6 的用户数据。
> 
> 
> 
> **查询并搜索数据 \(对应 ****`image_f747bf.png`**** 和 ****`image_f747c7.png`****\)**
> 
> 这段代码展示了一个相对复杂的“布尔查询（Boolean Query）”，模拟的场景类似：用户在一个搜索框里输入了“昵称”两个字，系统要在多个字段里找，同时又要排除掉某些黑名单用户。
> 
> 
> 
> - `GET /user/_doc/_search?pretty`：向 `user` 索引发送搜索（`_search`）请求。`?pretty` 是让返回的 JSON 结果排版更好看，方便人眼阅读。
> 
> - `"query" : { "bool" : {`：开启布尔查询。布尔查询允许你组合多个逻辑条件（并且、或者、非）。
> 
> 
> 
> - `"must_not" : [`：**条件一（非）**。里面的条件**绝对不能**满足。相当于 SQL 里的 `NOT IN`。
> 
> 
> 
> - `"terms" : { "user_id.keyword" : [ "USER4b...", "USER14...", "USER48..." ] }`：要求数据的 `user_id` 不能是这三个给定的长串 ID。通常用于排除已拉黑的用户、或者已经展示过的用户。
> 
> 
> 
> - `"should" : [`：**条件二（或者）**。里面的条件满足**任意一个**即可。相当于 SQL 里的 `OR`。
> 
> 
> 
> - `{"match" : { "user_id" : "昵称" }}`：去 `user_id` 字段里搜包含“昵称”的数据。
> 
> 
> 
> - `{"match" : { "nickname" : "昵称" }}`：去 `nickname` 字段里搜包含“昵称”的数据。
> 
> 
> 
> - `{"match" : { "phone" : "昵称" }}`：去 `phone` 字段里搜包含“昵称”的数据。
> 
> 
> 
> - *业务理解：这三个 **`should`** 就是全局搜索框的底层逻辑，无论用户的关键字命中 ID、昵称还是手机号，都会被搜出来。*
> 
> 
> 
> **删除索引 \(对应 ****`image_f747c7.png`**** 底部\)**
> 
> - `DELETE /user`：极其危险的操作。向 `user` 索引发送删除指令。这会**彻底销毁**前面第一步建好的表结构，以及第二步存进去的所有数据，通常用于重置环境或清空测试数据。
> 
>
